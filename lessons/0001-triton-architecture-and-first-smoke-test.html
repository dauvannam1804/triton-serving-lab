BÀI 0001 · Triton Serving & Performance · ~20 phút · hands-on trên máy bạn

Kiến trúc Triton & smoke test đầu tiên

Mục tiêu bài học: giải thích được Triton làm việc gì, và tự tay chạy được một server inference thật trên chính máy này — không GPU, không Docker — kèm kiểm chứng tự động.

Gắn với mission của bạn Task của bạn là "startup scripts, inference smoke tests" trong vai trò MLOps — Serving & Performance của dự án Cost-Aware GPU Scheduling. Bài này hoàn thành đúng 2 mục đó: một script khởi động (serve.sh) và một bộ smoke test. Toàn bộ benchmark/metrics sau này đều bắt đầu từ khả năng "bật server, xác nhận nó sống".

1. Triton làm gì? (3 phút)

Triton Inference Server là phần mềm phục vụ (serve) các model đã train xong: nó giữ model trong bộ nhớ, nhận request qua mạng, chạy inference, trả kết quả — và đo lường mọi thứ trên đường đi. Trong dự án của bạn, Triton chính là "cửa ngõ" mà mọi workload inference đi qua; bộ lập lịch GPU sau này sẽ dựa vào số liệu từ cửa ngõ này để ra quyết định.

📐 Sơ đồ kiến trúc & luồng dữ liệu Triton Inference Server
3 Cổng chuẩn Dynamic Batching Model Repo
1 Request vào: Client gửi request qua cổng :8000 (HTTP REST) hoặc :8001 (gRPC tốc độ cao).
2 Lập lịch & Batch: Scheduler xếp hàng và kích hoạt Dynamic Batching gom nhiều request thành 1 batch tensor.
3 Thực thi & Metrics: Backend tính toán với model đã nạp từ model_repository/, trả kết quả và cập nhật metrics (:8002).

Ba chi tiết kiến trúc cần nhớ từ tài liệu chính thức:

  • Model repository — một thư mục trên đĩa, Triton đọc để biết serve model gì.
  • Scheduler + backend — mỗi model có scheduler riêng (có thể gộp request thành batch), rồi đẩy cho backend tương ứng framework thực thi.
  • Ba cổng chuẩn — HTTP 8000, gRPC 8001, Prometheus metrics 8002 (Quickstart).

2. Giải phẫu model repository (5 phút)

Đây là repo thật đang nằm trong workspace của bạn — hãy mở và nhìn:

model_repository/
└── identity_cpu/
    ├── config.pbtxt        ← "hộ chiếu" của model
    └── 1/                  ← thư mục phiên bản (bắt buộc, tên là SỐ NGUYÊN)
        └── model.identity  ← file model (identity backend: file gì cũng được)

Quy tắc không thương lượng: mỗi model là một thư mục con, tên thư mục = tên model mà client sẽ gọi; bên trong phải có config.pbtxt và ít nhất một thư mục phiên bản đặt tên bằng số nguyên (1, 2…). Đây là lý do phổ biến nhất khiến model load fail (Model Repository guide).

config.pbtxt tối thiểu cần: tên, backend, và chữ ký vào/ra (tên + datatype + dims). Mở file model_repository/identity_cpu/config.pbtxt và đối chiếu: model identity là model "gương" — trả về đúng input nó nhận. Hoàn hảo để học cơ chế mà không tốn công tính toán.

3. Hands-on: bật server & smoke test (10 phút)

Mở hai terminal trong thư mục workspace. Terminal 1 chạy server, terminal 2 bắn test.

Bước 0 — Cài đặt (đã cài sẵn, script idempotent)

./setup_triton_cpu.sh

Nếu đã cài (máy này rồi) → mọi dòng in "đã có, bỏ qua". Chi tiết bản cài không Docker: REF 0001.

Bước 1 — Khởi động server (Terminal 1)

./serve.sh

Kiểm tra feedback ngay trên log — bảng trạng thái model phải hiện READY, và ba dòng "Started … Service" xuất hiện:

+--------------+---------+--------+
| Model        | Version | Status |
+--------------+---------+--------+
| identity_cpu | 1       | READY  |
+--------------+---------+--------+
... Started HTTPService at 0.0.0.0:8000
... Started GRPCInferenceService at 0.0.0.0:8001
... Started Metrics Service at 0.0.0.0:8002
Nếu FAIL Đừng đọc lan man — Triton luôn ghi reason ở dòng failed to load ... : <lý do>. Soi bảng xử lý lỗi trong REF 0001.

Bước 2 — Health check (Terminal 2)

curl -s -o /dev/null -w "%{http_code}\n" localhost:8000/v2/health/ready

200 — đúng nghĩa "server sống, mọi model READY". Mã khác 200 = chưa sẵn sàng. Đây là endpoint Kubernetes sau này sẽ dùng làm readinessProbe.

Bước 3 — Inference thật (giao thức KServe V2)

curl -s -X POST localhost:8000/v2/models/identity_cpu/infer \
  -H "Content-Type: application/json" \
  -d '{"inputs":[{"name":"INPUT0","shape":[1,4],"datatype":"FP32","data":[1,2,3,4]}],"outputs":[{"name":"OUTPUT0"}]}'
{"model_name":"identity_cpu","model_version":"1","outputs":[{"name":"OUTPUT0","datatype":"FP32","shape":[1,4],"data":[1.0,2.0,3.0,4.0]}]}

Soi feedback: data trả về đúng bằng input bạn gửi — model gương đang phản chiếu. Đổi [1,2,3,4] thành [9,8,7,6] và chạy lại để tự xác nhận cơ chế.

Bước 4 — Metrics (chốt smoke test)

curl -s localhost:8002/metrics | grep nv_inference_request_success
nv_inference_request_success{model="identity_cpu",version="1"} 1

Con số 1 = đúng 1 request thành công (bước 3). Gọi inference thêm 2 lần rồi curl lại — số phải tăng thành 3. Bạn vừa xác nhận được vòng đời đầy đủ: request → model → metrics, chính là data pipeline bạn sẽ tổng hợp làm báo cáo.

  • Bảng trạng thái hiện READY + 3 dòng "Started … Service"
  • /v2/health/ready trả 200
  • Inference trả đúng dữ liệu gửi vào
  • nv_inference_request_success đếm đúng số request

Ba của bốn mục trên ✅ = smoke test PASS. Đây chính là định nghĩa "server chạy được" bạn sẽ dùng trong mọi buổi demo với team.

Đọc sâu hơn (nguồn chính)

  • Nguồn chính của bài này: Triton Quickstart chính thức — đọc phần "Verify Triton Is Running Correctly" và "Send an Inference Request" (10 phút).
  • Công thức cài không Docker của máy này: REF 0001 — Triton CPU không Docker.
Đừng học một mình Bất kỳ bước nào chưa rõ — log khó hiểu, thuật ngữ lạ, vì sao phải dùng shape:[1,4] — hãy quay lại chat và hỏi thầy (agent). Mọi câu hỏi của bạn đều được ghi nhận để điều chỉnh bài sau.
Bài tiếp theo sẽ là gì? Sau khi smoke test pass: viết config.pbtxt cho model ONNX thật (không phải model gương) — nền của phần "Model repository/configuration" trong task. Nếu bạn muốn đổi hướng, cứ nói với thầy.
