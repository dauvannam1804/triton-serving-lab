2. Notebook Colab đã chuẩn bị sẵn (không phải gõ tay)

Mở colab/0005-triton-gpu-t4.ipynb trên Colab (File → Upload notebook, nhớ chọn runtime GPU). Notebook gồm 8 bước, mỗi bước một cell, tái dùng toàn bộ tài sản của 4 bài trước:

  • Bước 0 — probe: !nvidia-smi + parse driver, in ngay kết luận "được / rẽ nhánh".
  • Bước 1 — cài Triton: cùng recipe zip + extract openssl/DCGM + wheel CUDA như setup_triton_cpu.sh, nhưng không đụng apt của VM Colab.
  • Bước 2: git clone lab repo này — model repository, scripts, reports dùng nguyên xi.
  • Bước 3 — model nặng: sinh onnx_bigmatmul (matmul 512×512) ngay tại chỗ. Vì sao cần model thứ hai? onnx_linear tính trong ~10µs — GPU chẳng có việc gì làm, kernel launch (hàng chục µs) còn đắt hơn phép tính. Model nặng mới để GPU lộ giá trị.
  • Bước 4 — config GPU: chỉ khác CPU ở instance_group { kind: KIND_GPU count: 1 }. Quy tắc GPU: thường chỉ 1 instance — nhân bản model trên 1 GPU chỉ thêm tranh chấp, khác hẳn tư duy CPU nhiều core.
  • Bước 5–7: serve background + health check, inference smoke test (payload không đổi một ký tự so với CPU — client không cần biết nền là gì), perf_analyzer, DCGM metrics.
  • Bước 8: điền bảng cost so sánh.
Kỳ vọng đúng trước khi chạy Trên Colab có thể gặp: driver cũ hơn r580 (rẽ nhánh), link libssl khác Ubuntu 22.04 (xem log, thử extract deb 24.04 như notebook đã làm), quota GPU free hết (thử lại giờ khác). Mỗi vấp vált là một dòng ghi vào báo cáo cuối — "path đã thử, lỗi gì, xử lý thế nào" chính là giá trị của bài này, không phải "chạy được ngay".

3. Ba điều GPU sẽ dạy bạn mà CPU không thể (đọc trước khi đo)

a) Model nhỏ thì GPU… thua CPU

Với onnx_linear: CPU đáp ~430µs p50 (bài 0003) trong khi GPU cần ~hàng trăm µs–1ms chỉ để gửi work xuống GPU (kernel launch + PCIe + sync). Quy luật: dưới ngưỡng "đủ nặng", GPU là thuần overhead. Đừng ngạc nhiên khi thấy con số này trong perf_analyzer — đó là data, không phải lỗi.

b) Model nặng thì dynamic batching mới "về đúng chỗ"

Matmul 512×512 (batch 32) là mức đầu tiên GPU gai đuôi: compute một batch lớn chỉ chậm hơn ít so với batch nhỏ → gộp request ăn thưởng thật. So exec_count/request_count ở c=8 giữa 2 model sẽ thấy batching trên GPU đáng giá hơn nhiều batching trên CPU — khớp với lý thuyết ở bài 0002 mục 5.

c) Metrics lộ ra cả họ mới: DCGM_*

curl -s localhost:8002/metrics | grep -E '^DCGM_FI_DEV_(GPU_UTIL|MEM_COPY_UTIL|FB_USED)'
DCGM_FI_DEV_GPU_UTIL{gpu="0",...} 87
DCGM_FI_DEV_MEM_COPY_UTIL{gpu="0",...} 12
DCGM_FI_DEV_FB_USED{gpu="0",...} 1783

GPU_UTIL 87 khi perf_analyzer đang đạp tải = GPU bận gần hết giờ; FB_USED ~1.8GB = phần VRAM model chiếm. Cặp số này — utilization khi phục vụ tải — chính là thứ team scheduling cần để biết "1 GPU gánh được mấy model, mấy bản replica". Trên máy CPU-only của bạn, cả họ này vắng mặt (bài 0004 đã nhắc).

4. Kết quả cuối: bảng cost — ngôn ngữ chung của dự án

Bước 8 của notebook yêu cầu điền số vào bảng sau (cột CPU đã có sẵn từ reports/0001-cpu-baseline-onnx-linear.md):

ModelNềnThroughputp50 / p99Chi phíinfer/s mỗi $/h
onnx_bigmatmulCPU 8 core (máy Nam)bạn điềnbạn điền"miễn phí" (điện + thời gian)—
onnx_bigmatmulColab T4bạn điềnbạn điềnfree-tier (có quota) / ~$0.5/h nếu tính tiềnbạn điền

Công thức chuẩn của dự án — nhớ luôn số này:

cost_per_1M_inference = (giá_$mỗi_giờ × 1_000_000) / (throughput_infer_per_s × 3600)

Ví dụ phương pháp: nếu T4 cho 2 000 infer/s cho model X và giá thầu $0.53/h → ~$0.074 / triệu inference. Cùng model trên CPU hộp 8 core nếu đạt 500 infer/s "0 đồng" thì đáng chọn hơn khi nào? Khi tải thấp đủ để CPU kịp — và chính xác ở điểm tải nào thì phải đổi tàu là câu trả lời team scheduling cần từ bạn. Không có số trước, không có quyết định sau.
